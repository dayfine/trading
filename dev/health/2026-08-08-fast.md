## `FAIL:` substring is not a failure signal

`grep -c 'FAIL:' /tmp/runtest.log` returns **2** on a fully green run. Both
matches sit inside `PASS:` lines of `check_universe_deps_test`'s


anchored to line-start and remains correct -- `grep -n '^FAIL:'` returns
nothing here.)

## Settled this run: `dune runtest` DOES fail on a failing test

The 2026-08-07 summary carried an unresolved `[medium]`: two agents reported
different exit codes for the same mutation with the same failure count, one
remarking "dune doesn't fail on test failure, only build error". If that were
true, **every exit-code gate in this pipeline would be unsound**, so it was
worth settling rather than assuming.

Measured directly. Broke one OUnit assertion in `trading/base/status/test/status_test.ml`
(`assert_equal "test message"` -> `assert_equal "DELIBERATELY-WRONG"`) and ran
the scoped alias:

| state | command | exit |
|---|---|---|
| baseline | `dune runtest base/status/test` | **0** |
| one failing OUnit assertion | `dune runtest base/status/test` | **1** |
| restored | `dune runtest base/status/test` | **0** |

Failure output: `FAILED: Cases: 8 Tried: 8 Errors: 0 Failures: 1`.

**Conclusion: `dune runtest` propagates test failure as a non-zero exit.** The
2026-08-07 discrepancy was the `$?`-through-a-pipe trap, not a property of
dune. The exit-code gates are sound. Mutation reverted; tree verified clean.
