## The integrity linter caught an orchestrator error this run

Worth recording because it is the first time this check has fired on *my* edit rather than
an agent's. During the Step 5.5 reconcile I wrote

```
## Last updated: 2026-08-06 (orchestrator Step 5.5 reconcile: #2217 merged)
```

into `dev/status/screener.md` and an equivalent annotated date into `dev/status/harness.md`.
`status_file_integrity.sh` exited **1** with
`'## Last updated' is not YYYY-MM-DD`. Both were corrected to bare dates and the check
re-run to exit 0 before anything was committed.

Two things follow. First, the schema is stricter than it reads -- the field takes a bare
date and nothing else, so the natural instinct to annotate *why* the date moved has to go
in the body. Second, this is the concrete argument for running Step 6.2 with the **correct
path** rather than the one still documented in `lead-orchestrator.md`: the documented
invocation silently prints "No such file" while `$?` reads 0 from the pipeline tail, so a
run following the doc literally would have committed both malformed files and reported
"status integrity PASSING". See the daily summary's Escalations -- the fix remains blocked
on `.claude/**` write access.
