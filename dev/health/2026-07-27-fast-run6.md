## Findings

### F1 — Step 6.2's documented command has never actually run (8th run)

The path in `lead-orchestrator.md` Step 6.2 is wrong. Measured both forms this run:

| form | result | exit |
|---|---|---|
| `dev/lib/run-in-env.sh sh trading/devtools/checks/status_file_integrity.sh` | `sh: cannot open ...` | **2** |
| `dev/lib/run-in-env.sh sh devtools/checks/status_file_integrity.sh` | `OK: all dev/status/*.md files have required fields.` | **0** |

Cause: `run-in-env.sh` already `cd`s to the dune workspace root (`<repo>/trading/`), so the
script path must be relative to *that*. This run used the corrected form; the `0` above is a
check that genuinely executed.

**Second-order trap:** piping either form into `tail`/`head` before reading `$?` reports **exit 0
for both**, because in a pipeline `$?` is the last command's status. A run using the naive
`| tail -3; echo $?` idiom records a check that never ran as PASSING.

### F2 — `run-in-env.sh` is worktree-blind (NEW, severity high)

In `TRADING_IN_CONTAINER` mode, line 59:

```sh
PROJECT_ROOT="${GITHUB_WORKSPACE}/trading"
```

This ignores the current working directory. Any agent verifying a branch from a `git worktree`
therefore builds and tests **`main`**, not its branch, and gets a meaningless green. Contrast
line 65 (non-GHA path), which derives the root from the script's own location and *does* follow
a worktree.

Observed three times this run: found independently by qc-structural (#2135), confirmed from
source by the orchestrator, hit again by code-health (#2138). Two in-flight agents were
corrected mid-session; any worktree green reported before that correction is void.

Correct invocation from a worktree:

```sh
cd <worktree>/trading && eval $(opam env) && dune build
```

Filed as `H-RUNENV-WORKTREE-BLIND`. Same failure class as F2's second-order trap and F1: a
verification that reports success without having measured the thing it claims to.
