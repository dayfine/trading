## Root cause found for a 10-run-old finding: Step 6.2's documented invocation

Prior summaries have carried "Step 6.2's documented path is wrong" as an `[info]`
for nine consecutive runs without a diagnosis. Measured all four combinations
this run:

| invocation | exit |
|---|---|
| `sh trading/devtools/checks/status_file_integrity.sh` (from repo root, no wrapper) | **0** |
| `sh devtools/checks/status_file_integrity.sh` (from `trading/`, no wrapper) | **0** |
| `dev/lib/run-in-env.sh sh trading/devtools/checks/status_file_integrity.sh` (**as documented**) | **2** |
| `dev/lib/run-in-env.sh sh devtools/checks/status_file_integrity.sh` | **0** |

**The path is not wrong — the wrapper is.** `run-in-env.sh` cds into `trading/`
before executing, so the documented repo-root-relative path resolves to
`trading/trading/devtools/checks/...` and dies with
`sh: 0: cannot open ... No such file`.

Two clean fixes, either works:

1. **Drop the wrapper.** `status_file_integrity.sh` is plain POSIX shell over
   `dev/status/*.md`; it needs no opam env and no dune. `sh trading/devtools/checks/status_file_integrity.sh`
   from the repo root is exit 0 today. This is the simpler fix.
2. Keep the wrapper and make the path workspace-relative
   (`sh devtools/checks/status_file_integrity.sh`).
