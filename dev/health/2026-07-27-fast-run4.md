## The green is non-vacuous, and I nearly mis-reported it

Runs 2 and 3 both recorded the "green CI can be vacuous" trap: a `dune runtest` exit 0
proves nothing if the target was served from cache. I used `--force`, and then verified
the load-bearing target actually executed:

```
$ grep -c 'test_bayesian_opt\.exe\|test_bayesian_opt_cholesky\.exe' gate_runtest.log
2                                    <- both binaries invoked in the forced traversal

$ ./_build/default/trading/backtest/tuner/test/test_bayesian_opt.exe
Ran: 46 tests in: 1.63 seconds.  OK        exit=0
$ ./_build/default/trading/backtest/tuner/test/test_bayesian_opt_cholesky.exe
Ran: 8 tests in: 0.26 seconds.   OK        exit=0
```

**A caveat on my own method, recorded so the next run does not repeat it.** My first check
grepped the log for the capitalised OCaml module name `Bayesian_opt` and got **0 hits**,
which is exactly the signature run 3 documented for a cached, never-executed target. I
briefly believed the green was vacuous. The log actually contains the *lowercase binary*
name (`./test_bayesian_opt.exe`); my grep string was wrong, not the gate. The lesson is
narrow but real: when checking whether a target ran, grep for the **binary name dune
prints**, not the module name -- and confirm the pattern matches something on a known-good
run before concluding it matches nothing.

## Step 6.2 path bug -- now traced to a permissions dead end (7th run)

`lead-orchestrator.md` Step 6.2 documents:

```
dev/lib/run-in-env.sh sh trading/devtools/checks/status_file_integrity.sh
```

`run-in-env.sh` already `cd`s to the dune workspace root (`<repo>/trading/`), so the
correct path is `devtools/checks/...`. Measured this run:

```
documented form -> sh: cannot open trading/devtools/checks/... ; TRUE exit=2
corrected  form -> OK: all dev/status/*.md files have required fields ; exit=0
```

**Two things are new this run.** First, a second-order trap: piping either form into
`tail` before reading `$?` reports **exit=0 for both**, because `$?` in a pipeline is the
*last* command's status. A run using the naive `| tail -3; echo $?` idiom would record the
never-executed check as PASSING. Second, and more important: **I attempted to fix the doc
and was denied write permission on `.claude/agents/lead-orchestrator.md`.** Run 3 recorded
that a *writer agent* was blocked on this file and assumed the orchestrator could fix it.
The orchestrator cannot either. That is why the bug has survived seven runs -- it is not
inattention, it is that no automated actor can reach the file. Escalated with an exact
patch.
