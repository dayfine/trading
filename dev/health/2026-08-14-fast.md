## Environment measurement — dune lock isolation (corrects a 2026-08-13 claim)

The 08-13 summary recorded: *"Separate `git worktree`s do **not** give separate
dune locks here, because `run-in-env.sh` resolves them into the same workspace."*
**That is wrong**, and it imposed a false serialisation ceiling on that run.

Measured directly this run with the wrapper's `RUN_IN_ENV_PRINT_ROOT=1` seam:

| invocation | resolved PROJECT_ROOT |
|---|---|
| main checkout, relative | `/__w/trading/trading/trading` |
| worktree cwd, **its own** copy, relative | `/tmp/wt-probe/trading` |
| worktree cwd, **main's** copy by absolute path | refuses: "PROJECT_ROOT is ambiguous", exit 1 |

The dune lock lives at `<PROJECT_ROOT>/_build/.lock`, so a worktree invoking its
own wrapper relatively gets its **own** `_build` and its **own** lock. Row 3 is
the real hazard the 08-13 run hit — and since the H-RUNENV-WORKTREE-BLIND fix it
fails **loudly** rather than silently building the wrong tree.

Practical consequence: writer agents in GHA should each work in their own
`git worktree` and invoke `./dev/lib/run-in-env.sh` **relatively** from inside it.
That removes both the lock contention *and* the shared-working-tree collision
that Step 4's documented "git checkout -b in the shared tree" would otherwise
cause with parallel agents. Cost is a cold `_build` per worktree (no shared dune
cache configured: `~/.cache/dune` is 28K, `DUNE_CACHE` unset).

Runner capacity measured this run: 60 GB free disk, 15 GB RAM (13 GB available),
4 cores; a warm `trading/_build` is ~4.2 GB. This is a GHA runner, **not** the
7.75 GB local container that `container-capacity-scheduling.md` describes — that
rule's agent caps do not transfer directly.
