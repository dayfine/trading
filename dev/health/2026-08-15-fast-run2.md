Prior runs ran the whole-repo target locally as a third data point. I did not,
and the omission is a decision rather than a gap:

- CI already ran exactly that target on exactly this SHA and it passed. A local
  re-run is a second sample of the same measurement, not a new one.
- The one known-flaky test in that target, `test_csv_snapshot_builder_cleanup`,
  is **load-correlated** — that correlate was established by run 1 today
  (`dev/status/cleanup.md`): the orchestrator measured exit 0 on an idle box
  while an agent measured exit 1 on pristine `origin/main` with 2-3 concurrent
  cold builds live. Two feat-agent builds were running while I would have run it,
  i.e. precisely the condition that manufactures the false red.

Running it here would have had a materially higher chance of producing a
misleading failure than of finding a real one. The scoped `devtools/checks`
target — the code actually touched this run — was run instead, and is green.

| invocation | exit |

| `sh trading/devtools/checks/status_file_integrity.sh` (repo root, no wrapper) | **0** |

It is a **wrapper bug, not a path bug**: `run-in-env.sh` cds into `trading/`
first, so the documented repo-root-relative path resolves to
`trading/trading/devtools/checks/...`. The error text now confirms the mechanism
directly. Cheapest fix: drop the wrapper from Step 6.2 — the script is plain
POSIX shell over `dev/status/*.md` and needs no opam env. Blocked on `.claude/**`.
