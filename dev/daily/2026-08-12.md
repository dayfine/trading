## The defect, precisely

`orchestrator.yml:332` looks up today's summary correctly — it is date-scoped:

```sh
SUMMARY="$(ls -t dev/daily/${DATE}.md dev/daily/${DATE}-run*.md 2>/dev/null | head -n 1 || true)"
```

Line **334** is the bug. When that returns empty, it globs **every** summary ever
written and takes the first:

```sh
SUMMARY="$(ls -t dev/daily/*.md 2>/dev/null | grep -v -- '-summary\.md$' | head -n 1 || true)"
```

So a run that wrote nothing does not fail — it inherits. And the `Fail on
escalations` gate then greps *that* file, meaning a run that died before writing
its own `[critical]` is graded on someone else's clean summary and reports
success.

**`ls -t` is not "usually the previous run" — it is arbitrary.** On a fresh
`actions/checkout` every file carries the checkout mtime, so the ordering is
checkout order. From this run's own tree, 1 ms apart, in the wrong direction:

```
2026-08-12 12:37:05.363595298 +0000  dev/daily/2026-08-09.md       <- ls -t ranks first
2026-08-12 12:37:05.362595291 +0000  dev/daily/2026-08-09-run2.md  <- the actual latest
```

That is why the three surviving runs each picked a *different, progressively
older* file. It also affects **the orchestrator's own Step 1b**, which uses the
same idiom to find the prior summary for drift detection — I hit it this run and
had to correct for it by hand.

One trap for whoever fixes this: **plain `sort -r` is also wrong.** `-` (0x2D)
sorts before `.` (0x2E), so `2026-08-09-run2.md` sorts *before* `2026-08-09.md`.
The correct key is `(date, run_number)` with the un-suffixed file treated as run 1.

## Step 0.5 has a second gap, and it is why nothing rescued the strandings

The three surviving runs fast-exited while #2265 and #2266 sat reviewed and
unmerged. Condition 1 asks whether `tip_SHA == Reviewed_SHA` — i.e. "has anything
*new* been pushed since QC?" For both PRs the answer was no, so the queue read as
"saturated, nothing to do."

But **"reviewed" is not "finished."** #2265 was carrying a behavioral
**NEEDS_REWORK** that nobody had acted on, and #2266 had a structural APPROVE with
**no behavioral review ever run**. Both needed a dispatch; neither had new commits.
The condition cannot tell "reviewed and done" from "reviewed and awaiting the next
step," so it treats an actionable queue as a quiet one.

`A-FASTEXIT-VACUOUS` already covers the *empty*-queue case. This is the mirror
image — a **non-empty queue whose every PR is mid-pipeline** — and it is not
covered. Condition 1 should additionally require that each open PR is in a
terminal state (merged, or APPROVED-and-mergeable) rather than merely
un-re-pushed.
