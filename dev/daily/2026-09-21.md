## The find: the gate reader is blind on exactly the PRs worth reading

Following the priorities doc's P0 — *"run `sh dev/scripts/pr_gate_status.sh 2884`"* —
produced this:

```
$ sh dev/scripts/pr_gate_status.sh 2884
PR     CI       STRUCT         BEHAV          CODEX          NEXT-ACTION
-------------------------------------------------------------------------------------------
dev/scripts/pr_gate_status.sh: 663: jq: Argument list too long
$ echo $?
126
```

`pr_gate_status.sh` is the tool `.claude/rules/pr-gate-loop.md` tells every
session to run **instead of remembering state** ("Read the state, don't remember
it"). On the only open PR in the repo, it returned an empty table.

**Root cause, measured not guessed.** `_pr_meta_curl()` passes three full REST
payloads to `jq` as *command-line arguments*:

```sh
jq -n --argjson pr "$_pr" --argjson files "$_files" --argjson reviews "$_reviews" '{...}'
```

| payload | bytes |
|---|---:|
| `pulls/2884` | 20,855 |
| `pulls/2884/files?per_page=100` | **145,227** |
| `pulls/2884/reviews?per_page=100` | 3,789 |

`ARG_MAX` here is 4,194,304 — so the ~170 KB total is **not** the binding limit,
and "too many arguments" is the wrong diagnosis. The binding limit is Linux's
**per-argument** cap `MAX_ARG_STRLEN` = `PAGE_SIZE * 32` = **131,072 bytes**. The
`files` payload alone exceeds it. One oversized argument is sufficient; argument
*count* is irrelevant.

The payload is large because REST embeds a `patch` per file and #2884 commits
three 700-line `trades.csv` artifacts. So this trips on **any** experiment-results
PR, golden refresh, or fixture-heavy change — 30 files here, far under the
`per_page=100` ceiling.

**Why this is worse than exit 126 suggests.** The script does exit non-zero. But
the *visible* output is an empty table, which reads as "no PRs match" rather than
"the reader broke" — and our own docs invoke it piped (`| head`, `| tail`), where
the pipeline takes the last command's status:

```
$ sh dev/scripts/pr_gate_status.sh 2884 | tail -3 ; echo $?
0
```

A green-looking result indistinguishable from a real one — the repo's own named
defect class (#2741, #2747, #2771, #2803, #2810), now in the instrument we use to
detect it.

**Filed as issue #2886** with the measurement, the `MAX_ARG_STRLEN` mechanism, and
a two-part fix: (a) pass payloads via `--slurpfile`/stdin instead of argv, which
removes the cliff rather than raising it — narrowing the payload alone just lowers
the constant until the next large PR; and (b) render an explicit error row so a
piped caller that loses `$?` still sees the failure. Dispatched this run (below).

I read #2884's gates directly from REST for the rest of this run rather than
trusting the tool.
