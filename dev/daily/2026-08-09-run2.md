## The finding of the run: a reviewer caught a regression inside a correctness fix

F3 said `trade_audit_report_bin.ml` reads the raw price basis in two places where the domain wants adjusted — "the G14 split pathology relocated to the reporting layer." Both sites were changed. **One of the two was a regression**, and qc-behavioral found it by refusing to accept the author's justification at face value.

The author's stated reason for moving `_bar_close_of_reader` to adjusted was that both its consumers "divide a mark by an earlier mark." That is true of `Html_report._benchmark`. It is **false** of `_utilization`, which computes `Σ(i_qty × c) / nav` — it *multiplies* the mark by a share count. The reviewer traced both other terms to source and found both on the **raw** basis (`i_qty` ← `round_trip_pairing.ml:72-74`, `nav` ← `portfolio_valuation.ml:57-61`), then did the algebra:

- **pre-PR:** `deployed = true_deployed × S(d→exit)` → **exact** for any hold not straddling a split
- **post-PR:** `deployed = true_deployed × D(d→T) / S(exit→T)` → wrong for **every** trade in a symbol that split or paid a dividend after the trade closed

with measured magnitudes from the fixtures: KO **−27.5%**, JNJ **−24.0%**, AAPL **−77.9%**. Pre-PR that consumer was right in the common case; post-PR it was wrong in the common case, and **nothing at any layer would have caught it** — the author had already self-reported (G1) that the exe's wiring is unpinned.

The rework took the reviewer's recommended option: **narrow the PR.** The R6 half — unambiguously correct, and the half with the real measured payoff — landed. The benchmark half is deferred to **G4** with the derivation and the measured numbers inlined so nobody re-derives them.

What makes this worth the round-trip rather than a process tax: the *first* review had already verified every number in the PR body as exact. The defect was not in the measurements, it was in a claim about a consumer's arithmetic that nobody had checked. That is precisely the surface qc-behavioral exists for, and it is not reachable by CI.

## The CI failure I could not have seen from inside, and why

`#2252`'s `build-and-test` went red on a single line:

```
(cd _build/.sandbox/e1ce1e.../devtools/checks && /usr/bin/sh ./tracked_artifact_linter.sh)
fatal: detected dubious ownership in repository at '/__w/trading/trading'
```

The new linter shells out to `git ls-files`. In GHA, `actions/checkout` *does* add the repo to `safe.directory` — but into a **temporary `HOME`** (`/__w/_temp/<uuid>/.gitconfig`, visible in the job log as *"Temporarily overriding HOME…"*). The dune sandbox subprocess does not inherit it, so every `git` call fails and the check dies with **no `FAIL:` line naming a cause**.

**Three agents ran this check and all three saw it pass — because of me.** At Step 1 I ran `git config --global --add safe.directory /__w/trading/trading` so my own `git log` would work. That wrote to the real `~/.gitconfig`, which every agent in this shared container inherits. The author's green, qc-structural's green, and qc-behavioral's green were all artifacts of my environment setup. CI was the only clean room.

I verified the diagnosis myself rather than relaying it:

```
$ env HOME=/tmp/nohome git -C /__w/trading/trading ls-files -i -c --exclude-standard
fatal: detected dubious ownership in repository at '/__w/trading/trading'
EXIT=128

$ env HOME=/tmp/nohome git -c safe.directory=/__w/trading/trading -C ... ls-files -i -c --exclude-standard
→ exit 0, 1334 paths
```

So the targeted `-c safe.directory=<root>` form suffices; `*` is not required. This is now a standing trap for **any** future check that shells out to `git`, and it is invisible to local verification in this container.
