### The #2152 finding worth reading — the cleanup item's own numbers were wrong

The task was mechanical: a docstring claimed the test fixture `_well_conditioned_spd` was
"strictly diagonally dominant (hence positive-definite)", which is false, so replace it.
The risk in that task is subtle — replacing a wrong justification with a *differently*
wrong one is a regression that looks like a fix, because the new text appears freshly
measured.

So the brief said to verify the finding's numbers before restating them. The implementer
did, and they did not hold. Three independent instruments now agree:

| n | rows violating dominance | worst margin | λ_min |
|---|---|---|---|
| 4 | 0/4 | +1.4583 | 1.8691 |
| 32 | **9/32** | −0.4101 | 1.8289 |
| 100 | **61/100** | −1.5086 | 1.8278 |

The originating finding said dominance broke at **n=100** and λ_min ≈ **1.69**. It breaks
at **n=32** among certified sizes (n=21 absolutely), and λ_min is **1.83**. The three
instruments were deliberately different: the implementer's pure-OCaml power iteration, my
own Python power iteration on `(cI − A)`, and the behavioral reviewer's **LDL^T
negative-pivot count with bisection** — which is a *certificate* via Sylvester's law of
inertia (0 negative pivots at σ=0 proves positive-definiteness) rather than an estimate.
All three agree to four decimals.

**The reviewer then explained where 1.69 came from, which is the part worth keeping.** It
is within rounding of `1 + ln 2 = 1.6931` — the Toeplitz-symbol lower bound for this
matrix. The original finding reported **a valid lower bound as if it were the
eigenvalue**. That is a repeatable failure mode precisely because the number is not
random: it is correct, for a question nobody asked. Recorded in `dev/reviews/cleanup.md`.

A note on why this fixture resists the obvious tool: for a symmetric matrix the
**Gershgorin lower bound *is* the diagonal-dominance margin**, which is −1.51 here. So
Gershgorin cannot certify PD for this matrix — which is exactly why the old docstring's
reasoning failed in the first place. I did not see that when I wrote the review brief and
told the reviewer to use it; see §My own errors.

  fatal: 'ops/daily-2026-07-28-run2' is already checked out at '/tmp/ops-run2'

  Run 2's orchestrator had created a worktree at `/tmp/ops-run2` for its Step 8 push and left
  it there; git refuses to check out a branch already checked out elsewhere. **Note the
  ordering — `Removing dev/budget/…json` runs *before* the fatal.** The step's `git checkout`
  deleted the freshly-generated record, then aborted before committing anything, so it reached
  neither the PR nor the `ops/budget-*` orphan fallback. Confirmed: no
  `ops/budget-2026-07-28-30380136239` branch exists while all four other runs that day have
  one. **This means `A-BUDGET-ORPHAN` under-describes the risk — records are not merely
  stranded, they can be lost.** Second-order: step 10 `Fail on escalations` is `skipped` when
  step 9 fails, so the escalation gate did not run at all — the same unsoundness
  `A-SUMMARY-STALE-FALLBACK` describes, reached by a different path.

  **This is systemic, not a slip.** Step 4's GHA guidance (`git checkout -b` in the shared
  tree) is wrong, so runs 1, 2 and 3 all overrode it with `git worktree add` — while the
  bundling step was written against the checkout-based assumption it replaced. The workaround
  for one defect triggers another: *the more faithfully an orchestrator follows current best
  practice, the more likely it fails at step 9.* Cheapest fix is to make the bundling step
  worktree-proof (`git worktree prune` + explicit removal, or avoid checkout entirely); a
  strictly-better companion is to commit the budget record *before* any checkout that can
  remove it, which converts total loss into the milder orphan case. **Interim mitigation I
  applied, needing no workflow change: do not leave a worktree on the `ops/daily-*` branch at
  exit.**
