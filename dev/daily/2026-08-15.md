## The `ops(budget)` review bypass: root cause found, and it is one line

This has been filed as an escalation for eight consecutive runs and is the
maintainer's stated #1 question. Prior runs described the *symptom* correctly
and proposed guards against it (a path check that `ops(budget)` PRs touch no
`*.ml`/`dune` file; an empty-diff-vs-base check). **Both are the wrong fix,
because the cause is not a policy gap — it is a branch-base bug.**

Measured this run. All three cited PRs, merged with **0 reviews**:

| PR | title | non-doc code it actually carried |
|---|---|---|
| #2224 | `ops(budget): record 2026-08-06-…` | `segmentation_test.ml` +31, `trend/test/dune` +1 |
| #2235 | `ops(budget): record 2026-08-07-…` | `trade_audit_report.ml` +62, `.mli` +28, its test +204 |
| #2309 | `ops(budget): record 2026-08-13-…` | `linter_file_length.sh` +183, its test +255, `dune` +23 |

**~787 lines of production and test code merged with zero review**, under titles
announcing a JSON cost record.

Now the commit lists, which is the part that identifies the cause:

```
#2309:  93f97e7e  harness: close the .mli blind spot in linter_file_length.sh (P0.1)
        a7de3723  fix(gate): exclude *.pp.mli from the .mli file-length scan
        6726895a  ops(budget): record 2026-08-13-31700595897 ($32.1972)

#2235:  cde30208  feat(backtest): render the split-safe basis tally + inert fraction …
        7f0dadd0  ops(budget): record 2026-08-07-31178553959 ($21.3693)
```

The budget commit is the **last** commit on each branch, not the only one. The
branch carries whatever was already sitting on the runner's HEAD.

**`orchestrator.yml:482`:**

```sh
git checkout -b "ops/budget-${BUDGET_BASENAME}"
```

No base ref. The fallback branch is cut from **the runner's current HEAD**, which
by that point in the job holds commits left behind by the run's own agents. The
subsequent `git add "$OUT_FILE"` correctly stages only the JSON — but the *PR
diff* is branch-vs-`main`, so every pre-existing commit rides along. The PR body
then asserts, in good faith and wrongly, *"Additive observational data only."*
`merge_pr_when_clean` auto-merges it with no review gate.

**The fix is one line:**

```sh
git fetch origin main && git checkout -B "ops/budget-${BUDGET_BASENAME}" origin/main
```

That makes the diff exactly one JSON file, makes the PR body's claim true, and
makes review-free auto-merge of that PR *safe* rather than merely *tolerated* —
which is the property the proposed path-check guards were trying to approximate
from the outside. Blocked on `.github/workflows/**` (needs a `workflow`-scoped
PAT — the same blocker as #1636 and H-BLAS).

If you want defence in depth as well, the empty-diff-vs-base check is still
worth having. But it should be the backstop, not the fix.

## Three rejections for the same defect class, and what finally broke the loop

PR #2327 fixes two comment-parsing bugs in `check_universe_deps.sh`. Its code has
been correct since 08-14. It was rejected three times running, always for the
same reason: **the code was right and something written about it was not.**

| tip | the claim | why it failed |
|---|---|---|
| original | dune s-expressions cannot contain `;` inside quoted strings | **false** — measured; dune accepts it |
| `f560d71b` | a `\"` escape matches how dune escapes quotes | **false and unpinned** — deleting the guard left 18/18 green |
| `f3a20a78` | the scan "can only ever SUPPRESS a toggle… can never destroy live rule text" | **false** — counterexample below |

Each attempt answered the previous rejection by writing a **stronger, more
general** safety claim. Each was falsified. That is the drift the rework cap
exists to interrupt, and yesterday's run stopped at it for exactly that reason.

**Today's iteration-1 rejection is the sharpest of the three.** qc-behavioral
extracted `strip_trailing_comment_line()` into a standalone awk harness:

```
IN                    :   (setenv A "x\\" B "y; z" (run sh %{dep:c.sh})))
OUT shipped           :   (setenv A "x\\" B "y                <- run-target DESTROYED
OUT with guard removed:   (setenv A "x\\" B "y; z" (run sh %{dep:c.sh})))  <- PRESERVED
```

The premise was true — the scan only ever suppresses toggles. **The inference was
invalid, because quote state is a parity bit, not a monotone flag.** A suppressed
*closing* toggle leaves `inquote` stuck at 1; the next real `"` flips it to 0
while dune is still inside a string, and a live `;` past that point is read as a
comment leader. So on that input the guard is **worse than no guard** — which
also kills the charitable "conservative relative to the unguarded baseline"
reading.

### What I changed in the brief, and why it mattered

For iteration 2 I did **not** ask for a better-worded safety property. The
instruction was: **delete the universally-quantified claims outright**, state the
mechanism and the bounded limitation, and assert no property you cannot point at
a test for. Reasoning: three attempts had failed at the same task, so the task
itself was the problem — a universal claim about a single-line parity scan is
exactly the kind of statement this code cannot support.

The shipped text now says the scan "is not a bound on it… a real gap in this
scan", and names the mechanism transition by transition. qc-behavioral re-ran its
own counterexample, traced the parity state (suppression at pos 17 → inverted
parity → scan closes at pos 21 while dune opens → truncation at pos 23),
independently verified the reachability claim (the only dune file under that
directory contains **no backslashes at all**), and closed the CP4 finding:
**APPROVED, quality 4.**

**The generalisable point:** when three successive fixes fail the same way, the
next fix should change the *shape* of the answer, not its wording. A comment that
says less and is true is a better artifact than one that says more and is false —
and here "say less" was the only reachable correct answer, because the property
being asserted was not true of the code at any strength.

## #2334 — closing a gap that had already put a false verdict on record

`record_qc_audit.sh` invoked `gh` as `... 2>/dev/null || true`, discarding stderr
*and* exit code. A rate-limited, unauthenticated, or network-failed `gh` therefore
produced empty output **indistinguishable from "this PR has no reviews yet"**, and
the script fell through to reading `dev/reviews/<feature>.md` — which can belong
to a different PR entirely. The guard directly above it records the consequence:

> Observed in production: a NEEDS_REWORK PR got recorded as APPROVED this way,
> resetting the `consecutive_rework_count` streak #2123 exists to protect.

Now only "exit 0 + empty stdout + no stderr" may fall through; anything else
refuses loudly. 5 new scenarios (49 → 54 assertions), each stubbing `gh` via
`RECORD_QC_AUDIT_GH_BIN` **and pairing it with a `dev/reviews/` fixture holding a
deliberately wrong verdict**, so a silent fallback is caught by the record's
*content*, not merely by an exit code. Mutation discrimination was exact:
reverting the whole change reddens 32/33/34; dropping only the exit-code check
reddens **33 alone**; dropping only the stderr check reddens **34 alone**.

**qc-behavioral APPROVED (4) with one real, non-blocking finding, which I asked it
to look for.** I put the doubt in its brief explicitly — *is "any stderr ⇒ refuse"
gated on empty stdout, or does it fire even on a successful review-bearing call?*
It measured rather than reasoned: a stub exiting **0** with a full two-review
payload plus one `A new release of gh is available...` line on stderr produces
**exit 1, zero records**, and the self-contradictory message `failed (exit 0)`.

It judged this a follow-up rather than a blocker, and the reasoning is worth
keeping: gh's update notifier requires `!isCI()` **and** TTY on both streams —
stdout here is a command-substitution pipe and GHA sets `CI=true`, so the flagship
example is doubly excluded; and **the failure direction is right** — a loud absent
record is re-runnable, a false APPROVED corrupts the streak. It also verified the
one-line fix (gate the stderr arm on `[ -z "$BODIES" ]`) keeps the suite at 54/54
rather than guessing at it. Filed as `H-AUDIT-GH-STDERR-GATE-TOO-BROAD`.
