## The root cause behind a symptom four runs have been paying for

`anthropics/claude-code-action@v1` calls `configureGitAuth()` during
`prepareAgentMode`. In this container setup it **fails every run**:

```
Configuring git user...
Setting git user as claude[bot]...
fatal: not in a git directory
Failed to configure git authentication: ... ShellError: exit code 128
    at configureGitAuth (.../src/github/operations/git-config.ts:41:9)
    at prepareAgentMode (.../src/modes/agent/index.ts:61:13)
```

**It is universal, not a failure signature.** Occurrences of
`fatal: not in a git directory` in the raw logs:

| run | workflow | outcome | occurrences |
|---|---|---|---|
| 31679469222 | orchestrator | **success** | 2 |
| 31596975517 | orchestrator | **success** | 2 |
| 31388568372 | orchestrator | failure | 2 |
| 31575697571 | orchestrator | failure | 2 |
| 31404464033 | health-deep-weekly | failure | 2 |

Present in successful runs at the same count as failed ones — so it does not
fail a run; it silently leaves git unconfigured for the whole session. That is
exactly why every agent, and this orchestrator at 12:37Z, hits
`fatal: detected dubious ownership` on its first git command.

**Fix — one step, before the action, in each workflow that uses it:**

```yaml
- name: Mark workspace safe for git
  run: git config --global --add safe.directory "${GITHUB_WORKSPACE}"
```

`health-deep-weekly.yml` already does this — but only in a *later* step, and its
inline comment documents the symptom ("observed in run 24676096493 on
2026-04-20"). Known for four months as a quirk; actually a deterministic,
one-line-fixable defect.

Step 4's GHA guidance states that agent branches *"are independent so parallel
runs do not collide on the working tree."* **That is false.** In GHA the
orchestrator and every agent share one filesystem and one git working tree.

What actually happened, from three independent directions:

- **W1** (harness) began editing the shared checkout, noticed a sibling agent

  the shared checkout's branch — that sibling's uncommitted work rode along."*
- **I** pushed the summary checkpoint by running `git checkout -B` **in the
  shared tree while W2 was live** — 39 seconds after its last commit. Had it
  been mid-edit, that work would have been lost.

Nothing was actually lost, by luck and by W1's good judgement. The fix is
mechanical and belongs in Step 4: **every writer, and the orchestrator itself,
must work in its own `git worktree`.** For the rest of this run the orchestrator

### #2308 — close the `.mli` blind spot in `linter_file_length.sh` (P0.1)

The measurement determined the design. `*/lib/*.mli` — 439 files, never
scanned — has 14 files over the 300-line soft limit. But raw lines are the wrong
metric for an interface:

```
  raw  code  file
 1587    97  weinstein_strategy_config.mli
 1229   217  weinstein_strategy.mli
  534   150  trade_audit.mli
  ...
  301    46  stop_types.mli
```

**Every one of the 14 is docstring-dominated.** The worst raw offender carries
**97** signature lines; the maximum across all of them is **217**. A raw limit
would have reddened main on 14 files, none with an interface-complexity problem,
penalising documentation on the surface `qc-behavioral` treats as the primary
contract. Both escapes — bulk `@large-module` markers, or a limit bump chosen to
make the tree pass — are what `code-health-discipline.md` lists under *What NOT
to do*.

So: scan `.mli` against a **signature-line count** (raw minus `(* ... *)` blocks
minus blank lines) at the same 300/500/11 % thresholds. The tree passes cleanly
at max 217, **no exceptions, no markers added**.

Also in scope, and good: nested comments handled by a **depth counter** (OCaml
comments nest — a boolean toggle closes at the inner `*)` and leaks the
remainder as code); `.ml` behaviour byte-identical including the
`H-CHECK-SETE-DIAGNOSTICS` TOCTOU handling; `.ml`/`.mli` populations capped
**independently** so neither subsidises the other's opt-out budget; and the
missing `(glob_files_rec ... *.mli)` dune dep added, closing an
`H-CHECK-CACHE-BLIND` gap the rule had all along.

Test-file coverage (**401 files, 154 over 300, 70 over 500**, largest
