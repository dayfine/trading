## Two PRs, one table, two incompatible stories

Both PRs discuss the same artifact: the cell-00 rest-time measurement joining
`position_id → ticket_age_weeks_at_fill → pnl_dollars`. Neither author saw the
other's text.

**#2368** diagnosed the *earlier* version of that table as a **mis-join
artifact** — *"must have come from a symbol/date match"*, *"the signature of a
join that attaches the wrong money"*, *"Only the keyed column can be trusted"*.

**#2371** made the same move one level along: it disproved the join for **cell
13** (404 of 953 coverage) and then applied the **mis-join verdict to cell 00**.

Both are the repo's signature defect — a correct enumeration followed by a
sentence quantifying over a different set — and **both are refuted by the same
arithmetic**, which #2368's reviewer found and stated more sharply than the
original objection:

> A re-pairing permutation **preserves the total**. The old rows sum to
> **+2,173,658**, the new to **+2,314,953** — a **+141,295** move. Permuting
> money across the same round trips cannot do that. The counts also differ: old
> n's sum to **1,146** (the text said 1,145), new to **1,147**. **A mis-join
> within one artifact preserves n exactly.**

So the supportable claim is *"two measurements over different trade sets, not
reproducible"* — and **not** a causal account, per
`.claude/rules/mechanism-validation-rigor.md` §"Verdict calibration". Both PRs
now say that, in near-identical words, and each fences the cell-13 disproof to
cell 13 only.

`dev/agent-memory/project_rest_time_pnl_is_cell_specific.md` records the earlier
table as **already `position_id`-keyed** — so the mis-join story was contradicted
by its own provenance the whole time. It was available to both authors.

**The generalisable lesson is about ordering, not carefulness.** Neither author
was sloppy; both enumerated correctly. What neither could do was see the other's
PR. The orchestrator could — and the cross-PR check was worth more than either
individual review, because a defect that is invisible from inside each PR is
plainly visible across them. That check is now a standing item in the briefs.

## Where the dispatcher corrected a reviewer

Worth recording because it is the inverse of the usual direction, and because
following the review verbatim would have caused a live regression.

#2368's structural reviewer correctly found `WORK=/tmp/ttl-retest` writes to the
Docker **writable layer** rather than the bind-mounted `/tmp/sweeps/<name>` — the
failure class `sweep-hygiene.md` exists for, after the 2026-05-23/24 session lost
~16 hours to `Docker.raw` growth. Its prescribed fix: change `WORK` **"and update
`LOG_HOST` accordingly."**

I checked both variables before briefing the rework:

| var | side | evidence |
|---|---|---|
| `WORK` | **container** | `docker exec $C mkdir -p $WORK`; all 6 uses inside `docker exec` |
| `LOG_HOST` | **host** | `touch` and `tee -a` both run **outside** `docker exec` |

`LOG_HOST` is already host-side, so moving it gains nothing — and would have
broken two live things: it is the resume skip-predicate's source
(`grep -q "RESULT $tag " "$LOG_HOST"`) for **a chain that was in flight at that
moment**, and it is the literal path the priorities doc tells the next session to
`cat` first. Moving it would have silently blanked the resume state and re-run
every completed arm.

The review was **a correct diagnosis with a prescription quantifying over a wider
set than the diagnosis supported** — the same defect class the PR was being
reviewed for. The rework brief carried the narrowed instruction plus the reason,
and the author added a header comment recording *why* `LOG_HOST` deliberately
does not follow, so the next reader does not "fix" it for consistency.
