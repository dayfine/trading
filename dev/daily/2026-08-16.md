The rework agent **finished its job**. It addressed the reviewer's finding, and
took the optional-but-better branch of it — the reviewer had offered "narrow the
comment" as the minimum fix and "gate `:375`/`:384`/`:431` on `FILE_MODE`" as the

**Why this is not recoverable, and why that is the finding.**
`.claude/rules/pr-gate-loop.md` §"Dispatcher-side recovery" tells a dispatcher not
to re-dispatch reflexively — a stalled agent's commit usually still sits in its
workspace, and finishing it from the dispatcher side (`jj bookmark set` →
`jj git push`) is faster and cannot lose the work. **That recipe assumes a
persistent workspace.** On a GHA runner there is none: the container is torn down
with the job, and `jj` is broken here anyway. The recovery path the rules describe
does not exist in this environment, so an unpushed commit is not "stalled", it is
**gone**.

The mitigation is not a better recovery procedure, it is a stricter push
discipline — which `.claude/rules/worktree-isolation.md` §"Finish Protocol"
already states ("Never end a turn with an un-pushed commit… a green local build
that was never pushed is lost work"). The agent appears to have honoured commit
discipline and not push discipline. **I have re-dispatched the work with the lost
commit's own subject line quoted in the brief**, so the second attempt starts from
the first one's conclusion rather than from the reviewer's finding.

## Two one-line defects in a five-line log tail

**1. The bundling step collides with a worktree the orchestrator leaves behind.**
`fatal: '<branch>' is already checked out at '/tmp/ops-summary'`. Step 9 wants to
check out the daily-summary branch at a **fixed path**, and the orchestrator's own
Step 8 had already checked that branch out. Git refuses a second checkout of one
branch; `set -e` turns the refusal into exit 128. Consequences, both observed:
**#2336 was stranded open** (it is still open as I write this — I am merging it
this run), and the budget JSON for run 31884644256 never landed.

Fix is a `git worktree remove` / `--force` on the fixed path before the add, or a
per-run unique path. Blocked on `.github/workflows/**` (`workflow`-scoped PAT).
**I have worked around it on my side** by removing my summary worktree before
exit, so the branch is checked out nowhere when step 9 runs — but that is a
convention this run happens to follow, not a guarantee, and the next orchestrator
that forgets will strand its own summary the same way.

cutting the fallback branch from the runner's **dirty HEAD** instead of

## The capacity ceiling on this box is 2 build-heavy agents, not 3

`.claude/rules/container-capacity-scheduling.md` caps concurrent agents at 3. That
number is calibrated for the local ~8-core devcontainer. **This GHA runner has 4
cores**, and I dispatched three build-heavy QC agents into it at once. One starved:
it spent 20+ minutes unable to complete `dune build`, reported the stall as "dune
lock contention", and returned **NEEDS_REWORK on an environment failure** for a PR
it had otherwise found clean.

I inspected the live runner rather than accepting the diagnosis:

```
/tmp/qc-2349/trading/_build        15G, holds the only _build/.lock
/__w/trading/trading/trading/_build   absent
~/.cache/dune                      28K
load average                       10.43  (4 cores)
```

Each agent had its **own** worktree and its **own** `_build`, so there was no shared
lock to contend for and the shared dune cache is negligible. The mechanism is plain
**CPU starvation** — a cold OCaml build here is 10–20 minutes uncontended, and three
of them do not degrade gracefully. The distinction matters because "lock contention"
suggests a serialization fix and "starvation" correctly says *dispatch fewer*.

Two corrections applied immediately, both of which worked:

1. **A public annotation on #2348** recording that its NEEDS_REWORK is an ENVFAIL,
   not review feedback, with the measurements above — so the author does not act on
   it and a later reader is not misled by two verdicts at one SHA.
2. **Reclassifying dispatches as build-heavy vs shell-only.** The two rework agents
   this run touch only shell scripts; they were dispatched with an explicit
   instruction *not* to run `dune build`, and both ran happily alongside two cold
   builds. **The real cap is 2 build-heavy agents; shell-only agents are close to
   free.** That is a more useful rule than a flat count of 3, and it is what let this
   run keep four agents in flight without a second starvation.
