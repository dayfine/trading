### Measured this run: 3 concurrent agents is over the practical ceiling, and the cause is disk, not RAM

Mid-run measurement, with all three agents live:

```
shared checkout  trading/_build   absent          <- the workflow's restored cache is NOT in the worktrees
wt-fastexit-verify/trading/_build 16G             <- built
wt-qc-lexicon/trading/_build      absent          <- still queued on the mutex
wt-r7-forceliq/trading/_build     absent          <- still queued on the mutex
overlay 145G  100G used  45G free  (69%)
```

Two constraints compound, and they pull against each other:

1. **Worktree isolation is mandatory** (#2470 — four agents sharing one tree left
   one agent's finished work on another agent's branch). But a fresh worktree has a
   **cold `_build`**, and this repo's `_build` is **16 GB** — already a known
   harness item, `H-AGENT-WORKTREE-DISK-16GB-EACH`, measured 2026-09-05. Three
   agents therefore want ~48 GB against 45 GB free.
2. **The 1-dune memory cap serializes them**, so those cold builds do not overlap —
   they queue. Agent 1 built; agents 2 and 3 had done no `dune` work at all by the
   time this was measured.

The net effect is that raising the agent count past ~2 buys **no parallelism**
(the mutex serializes the expensive part) while multiplying the **disk** cost
linearly. The capacity rule caps on RAM, which is the right cap for *simultaneous*
links but does not capture this.

**Recommendation for the next run:** dispatch **2** agents, not 3 — or seed each
worktree's `_build` from the workflow's restored cache so the serialized builds are
warm. Notably the shared checkout's `_build` is *absent* here, so the workflow's
cache restore is not currently reaching anything the agents use; that is worth
checking before adding agents back.
