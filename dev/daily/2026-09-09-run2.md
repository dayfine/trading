### The uncomfortable part: this was caused by run 1's own mitigation

Run 1 opens by explaining that it published its summary **incrementally**, citing
the 09-08 run's conclusion verbatim: *"the general fix is publish incrementally
and treat the artifact as the deliverable, not make the final step more
reliable."* That is a correct fix for the five-lost-summaries defect (#2741 D2),
and it worked — you are able to read run 1's summary because of it.

But *"treat the artifact as the deliverable"* is only true when the artifact is
the deliverable. On a dispatch run it is **not**: the deliverable is the agents'
PRs, and the summary is a report *about* them. Having published, run 1 had
produced its stated deliverable and stopped.

**A mitigation that makes the deliverable durable can also make the run shorter.**
Five runs lost the report while doing the work; run 1 saved the report and lost
the work. The two failures look opposite and share a root: both treat one
end-of-run artifact as the thing that must survive, instead of asking what the run
was actually for.

The correction is not to stop publishing early — it is *"publish early **and** stay
until the agents return."* This run does both: this file was published before the
agents finished, and the run does not end until they are back and their branches
are on origin. **No `in flight` row will be left standing in the table below.**

verdicts.
