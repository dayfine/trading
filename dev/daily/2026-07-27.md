## Feature Progress

### weekly-snapshot — #2105 (Phase C renderer) and #2107 (#2103 reconciliation)

**#2105 — what it is, and what it is not.**
Four new modules: `html_report_renderer` (248 lines), `svg_chart` (171), `html_page`
(148), `report_shared` (80), plus `-html` / `-data-dir` on `render_weekly_report`.

The design decision I flagged at dispatch was resolved the right way. `Weekly_snapshot.t`
carries **no price history** — only scalars — so a chart needs bars from somewhere. The
author took the option that leaves the frozen schema alone: `render` accepts
`?bars_for:(symbol:string -> Types.Daily_price.t list)`. No schema bump, `render` stays
pure, and `svg_chart` "knows nothing about snapshots", so it is reusable by whatever
renderer replaces this one. Degradation with no bars is pinned by four tests, and the
*mixed* store case (some symbols present, others absent) is covered — that is the case
this kind of thing usually breaks on.

**The gap you should know about.** Measured against
`dev/notes/weekly-report-design-reference-2026-07-27.html`, which you committed ~40
minutes after I dispatched: **tag chips, card layout, 30-week MA line, TradingView links
and the order-ticket line are all absent** (0 occurrences each in the new modules). What
landed is a table report with per-row sparklines. Drop-reasons *are* covered, via the
Warnings section. The pure-geometry `svg_chart` is a reasonable base for the MA line and
labels, so the delta is additive rather than a rewrite — but it is a real delta and I did
not want it buried.

**#2107 — the correctness half, and why it is still open.**
`expected_fill_price` is the right idea: one function, called by `Trade_sizing` and both
renderers, so the arithmetic and the printed price cannot drift. The reviewer confirmed
**sizing is clean** — it reads that function and nothing else — and independently
recomputed the numeric pin (fill $107.30, stop $90.00 → 57 sh / $6116.10 / $986.10,
against 100 / $10,000 / $1,000 on the buggy path; all four asserted, so not label-only).

But the renderers never call it. Risk % still computes from `c.entry`, so a through-entry
row displays `10.0%` beside an instruction implying `16.1%`. That is #2103 again at
smaller scale, in the column named "Risk %" — and the row-substring pin the author added
locked the wrong value in, so the suite would have rejected the fix. Strong assertions
protect correct and incorrect behaviour equally; that is the lesson worth keeping.

Verified good and needing no action: the live-override arming **is R3-safe** — `git grep`
finds exactly one production read of either config field, inside `_reconcile_entry`,
reachable only from `generate`, never `on_market_close`, so arming cannot move a backtest
number. The Weinstein citation is verbatim. The short arm is correct and non-vacuous
(`test_same_close_classifies_oppositely_by_side` cannot be satisfied by a side-blind
classifier).
