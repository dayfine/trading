## #2628 — the #2626 fix, and the part of it that isn't pinned

`review_result` now falls back to the review's `commit_id` when the body carries
no `Reviewed SHA:` line. Body stays primary, so a review can still declare it
reviewed a different SHA than it was posted against. Second, smaller change:
`_pr_meta_curl` was widened to actually **project** `commit_id` — the prior
`map({body: .body})` dropped the field before the parser could ever see it, so
the fallback alone would have been inert.

RED/GREEN, measured by me directly:

| state | case 43 (sha-less body + STALE `commit_id`) | full suite |
|---|---|---|
| **RED** (fallback reverted) | `want stale(aaaaaaaa), got ok` | **exit 1** |
| **GREEN** (fallback restored) | `stale(aaaaaaaa)` | **exit 0, 54 clean** |

Base was 51 cases; three added. **But 43 is the only discriminator** — case 44
(sha-less + current-tip `commit_id` → `ok`) and case 45 (body SHA beats a
disagreeing `commit_id`) both pass with *or* without the fix. They are guards,
not pins, and the PR body says so rather than counting three where there is one.

**The residual I found while verifying, and did not paper over:** reverting
*only* the `_pr_meta_curl` projection — keeping the fallback — leaves the suite
**green, exit 0, 54 clean**. The suite hands `_gate` hand-built review arrays and
never exercises `_pr_meta_curl` at all, so **half this fix has no regression
pin**. A future revert of that one line silently restores the defect with a
green suite. Same shape as every other defect this lineage keeps producing, so
it is recorded in the PR body rather than left to be rediscovered.

**A claim I verified — and got half wrong.** The code comment and `harness.md`
both asserted the `gh` backend has "no `commit_id` field to widen into", so a
sha-less review in a *local* `gh`-backed session still reaches the always-current
path. qc-structural called this "plausible" and "reasonable", which is not a
measurement, so I checked it myself: `_pr_meta_gh` is
`gh pr view --json headRefOid,files,reviews,labels`, and that projection carries
no commit sha. I reported the claim **true**.

qc-behavioral then showed it is true of *that projection* and false as stated:
GraphQL's `PullRequestReview` type **has** a `commit` field, and
`gh api /repos/{owner}/{repo}/pulls/{n}/reviews` returns `commit_id` directly.
So the gap is a **backend choice closeable in about one line**, not an API
limit — and the original wording invites a future reader to treat it as
unfixable.

Worth being precise about my own error here: I verified the narrow proposition
(*does this command return the field?*) and reported it as the broad one (*can
`gh` reach the field at all?*). Checking the literal code was not the same as
checking the claim the code's comment was making.
