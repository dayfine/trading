## Feature Progress

### harness [MERGED #2199]
- **H-AUDIT-MODE-0600 closed.** `write_audit.sh` had been writing audit records `0600` instead of
  `0644` ever since #2169 — `mktemp` creates its file `0600` *by design, ignoring umask* (a
  security property of mktemp, not a bug), and `mv -f` preserves the source mode. There was no
  `chmod` between them, so a correctness fix silently changed output permissions.
- Fix is one line, and the **placement was argued rather than assumed**: `chmod` on the *temp file
  before* the rename, not the output after, so the record carries its final mode from the instant
  it becomes visible. Chmod-after-`mv` would leave a real (if microscopic) window in which the
  concurrent globbing readers — `consecutive_rework_count` and
  `deep_scan/check_06_qc_calibration.sh` — could `open()` it at 0600.
- **Regression pin** forces `umask 077` so a pass cannot be a coincidence of the ambient umask.
  qc-behavioral proved that forcing is *load-bearing*, not decorative (mutation M4b).
- **Why this mattered despite being functionally inert:** it composes with the defect #2184 just
  fixed — a record another user cannot read is precisely the grep-exit-2 "unreadable prior record"
  case, which gets *skipped* from the streak, under-counts `consecutive_rework_count`, and thereby
  **suppresses** the `>= 3` escalation.
- **The fix confirmed itself in production, by accident.** This run wrote two audit records, and a
  shared-tree collision (below) meant one had to be rewritten after the merge. Same run, same
  `umask 0022`, differing *only* in whether #2199 was in the working tree:

  ```
  -rw-------  dev/audit/2026-08-04-cleanup-...json   written BEFORE #2199 landed  -> 0600 (the bug)
  -rw-r--r--  dev/audit/2026-08-04-harness-...json   written AFTER  #2199 landed  -> 0644 (the fix)
  ```

  An unplanned natural experiment: the defect and its repair, observed side by side in the same
  session. Both records are committed in this PR, so the pair is durable evidence.
