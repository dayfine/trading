- **[info] The 27-run zero-dispatch streak was a search failure, not a work
  shortage — and this is the single highest-value finding of the run.** Runs 1–5
  today (and 22 before) concluded "every track is data-gated / human-gated /
  active-LOCAL." That conclusion was reached by scanning *track status files*,
  which are stale-prone. It was **not** cross-checked against the live P1 queue
  in the current priorities doc, where two dispatchable items sat in plain text:
  a named `Loader.load_exn` QC follow-up, and three filed-but-unowned bug issues
  (#2057/#2059/#2060). Both dispatched items produced real defect fixes.
  **Suggested change for `orchestrator-automation`:** add an explicit Step-1
  sub-step that parses the newest `next-session-priorities-*.md` §P1/§P2 and any
  open `bug`-labelled issues into the eligible-track set, independently of
  `dev/status/*.md`. A zero-dispatch verdict should require *both* sources to be
  empty. Note `#2059` and `#2060` remain open and unowned right now.
- **[info] Two of the four agent-authored deliverables would have shipped a
  latent defect without the QC loop; both were caught by qc-behavioral, not by
  CI.** #2073's first pass fixed one silent-drop and left its twin; #2074's first
  pass would have auto-closed a half-fixed bug. CI was green in both cases. This
  is direct evidence the two-stage QC gate is load-bearing, and that the
  intra-run rework loop (Step 5a) pays for itself — both were closed in
  iteration 1 of 2, within the same run.
- **[info] Recurring Step 0.5 Condition-1 false-negative on maintainer-LOCAL PRs.**
  Unchanged from run-5: the orchestrator will never produce a `Reviewed SHA:` for
  a maintainer-authored PR, so Condition 1 fails on every run they stay open.
  Suggested fix stands (exempt PRs classified active-LOCAL / advisory / docs-only,
  mirroring Condition 2's summary-commit exemption). **Caveat learned this run:**
  fixing this alone would have turned today's run into a NO-OP and the two defects

  making fast-exit easier.
- **[info] Documented `dev/lib/run-in-env.sh` linter invocation is wrong in
  `lead-orchestrator.md` Step 6.2.** The agent doc says
  `run-in-env.sh sh trading/devtools/checks/status_file_integrity.sh`, but the
  wrapper already cds to `<repo>/trading`, so the correct path is

  instead of checking the exit code would read as "clean." Also note the script
  is `status_file_integrity.sh`, not `status_file_integrity_linter.sh`. Worth a
  harness fix.
- **[info] GHA single-checkout / single-dune-lock is the binding throughput
  constraint.** Two build-agents cannot run concurrently (2026-07-19 incident,
  `harness.md`), and they cannot even hold different branches checked out. This
  run worked around it by (a) serializing all build-agents and (b) briefing QC
  agents to review read-only via `git show <sha>:<path>` with CI as the H1–H3
  evidence — which made QC safely parallelizable and is the main reason 10 agents
  fit in the window. **Recommend adopting the read-only QC brief as the default
  GHA pattern**, and consider `git worktree` isolation for build-agents.
