## The 08-13 dune-lock claim is wrong, and it cost that run throughput

The 08-13 summary recorded, as a `[high]` escalation:

> Separate `git worktree`s do **not** give separate dune locks here, because
> `run-in-env.sh` resolves them into the same workspace.

It concluded that dune-touching dispatches must be serialised, and called that
"a throughput ceiling this orchestrator does not currently model."

**Measured directly this run**, using the wrapper's own `RUN_IN_ENV_PRINT_ROOT=1`
testability seam:

| invocation | resolved `PROJECT_ROOT` |
|---|---|
| main checkout, relative | `/__w/trading/trading/trading` |
| worktree cwd, **its own** copy, relative | `/tmp/wt-probe/trading` |
| worktree cwd, **main's** copy by absolute path | refuses: `PROJECT_ROOT is ambiguous`, exit 1 |

The lock lives at `<PROJECT_ROOT>/_build/.lock`. Rows 1 and 2 resolve to
different roots, so they get **different `_build` directories and different
locks**. The wrapper's header documents this as deliberate design — it prefers
the cwd-derived candidate precisely so an agent in a worktree builds its own
tree.

Row 3 is the real hazard, and it is *not* silent lock contention: since the
`H-RUNENV-WORKTREE-BLIND` fix the wrapper **refuses to guess** and exits 1 with
both candidate paths printed.

So what actually happened on 08-13 is the simpler thing: those agents were
following Step 4's documented GHA path, which says to `git checkout -b` **in the
shared checkout**. One tree, one `_build`, one lock — contention guaranteed, and
worse, parallel agents stomping each other's working tree.

**The fix is a dispatch-shape change, not a serialisation ceiling.** Every writer
this run got its own `git worktree` and was told to invoke
`./dev/lib/run-in-env.sh` *relatively* from inside it. Both writers built
concurrently with my own full `dune runtest` on the main checkout, and none of
the three contended. Cost is a cold `_build` per worktree — there is no shared
dune cache configured (`~/.cache/dune` is 28 K, `DUNE_CACHE` unset) — which the
runner's 60 GB has ample room for.

Step 4's GHA dispatch instructions should be rewritten to prescribe worktrees.
Blocked on `.claude/**`.

with instructions to work in its own worktree, and it did; the `git checkout`
was a separate, well-intentioned act of housekeeping on a tree it did not own.

**Nothing was lost**, for one reason: I push after every summary commit, so all
three commits were already on origin and PR #2321 was intact. Recovery was a
single `git checkout`.

But the near-miss is the point. `dev/daily/2026-08-14.md` simply **ceased to
exist on disk** while I was still writing to it. Had I been mid-edit with
uncommitted changes — the normal state for a file I revise four or five times a
run — they would have been silently gone, and the next `Edit` would have failed
against a file that was no longer there.

`.claude/rules/worktree-isolation.md` covers agents *contaminating their own*
commits with the parent's state. This is the inverse: **an agent mutating the
dispatcher's checkout**. The rule's `jj workspace` guidance does not address it
because it assumes the hazard flows parent → child.

Two fixes, both cheap:
- QC agent briefs should say explicitly: **never run `git checkout`, `git switch`,
  or `git restore` in `/__w/trading/trading`** — work in your worktree, remove it,
  and leave the parent's HEAD exactly as you found it.
- The orchestrator should treat "push after every summary commit" as
  load-bearing rather than merely prudent. It already is, for a different reason
  (surviving mid-run death); this is a second, independent reason it pays.
