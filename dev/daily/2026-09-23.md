### The #2927 rework, and a conflict that silently suppressed CI

Worth separating three things that all landed on this one PR, because only the
middle one is a defect in the work itself:

**1. The behavioral finding was the run's best catch, and it came from
mutation, not reading.** The PR shipped with "23 mutations, zero surviving
mutants." qc-structural probed four surfaces the suite never touched and **three
survived**; qc-behavioral then widened it to **15 of 16 surviving**. The whole
`totals` block, `rows` ordering, `--until`, and **all table-mode content** were
asserted only by *key presence*, never by value. Magnitudes on the committed
fixture: dropping `cache_read` from `subagent_tokens` turns **4491 into 891**
(5×), and `main_tokens` **457063 into 7063** (65×). The test file's own header
says it exists to catch "a wrong number that still LOOKS like a report" — which
is verbatim what survived, on the two figures the report prints last and
largest, in a tool whose entire purpose is numbers people will act on.

Both reviewers declined to overreach: structural explicitly declined to score it
as a structural FAIL ("no checklist row covers it; inventing one would be
overreach") and **routed it to behavioral as contract-pinning territory**. That
hand-off is the two-gate design working as intended rather than one reviewer
stretching.

**2. The rework closed it and then went one step further.** 33 → **50**
assertions, **17/17** mutations caught, and `dev/scripts/token_usage_report.sh`
**byte-identical** to the reviewed tip — additive test coverage only, exactly as
scoped. The agent also found that *the reviewer's own prescribed `--top 1`
assertion had the same hole the review was about*: it greps the suppression
**notice**, which survives a mutation dropping the `.rows[0:$top]` slice. It
implemented the prescription verbatim **and** paired it with a row-count
assertion pinning the truncation itself. qc-structural independently confirmed
that the prescribed assertion stays green under that mutation and only the added
one catches it — so implementing the review literally and stopping would have
left a live mutant. Pinning the announcement of a behaviour rather than the
behaviour is a shape worth naming; it recurred inside the review that was about
it.

**3. A conflict silently suppressed CI — and "no checks" read as "checks
pending", not as "blocked".** After #2929 merged, #2927 went
`mergeable_state=dirty` (both PRs append to `dev/status/harness.md` *and*
`trading/devtools/checks/dune`). GitHub cannot build the merge commit for a
conflicted PR, so it **never queued any workflow** — `check-runs` returned
`total_count: 0` indefinitely. That is a genuinely confusing signal: an empty
check list looks like "CI hasn't started yet" and would resolve itself on a
normal PR, so waiting is the natural and wrong response. The tell was
`mergeable_state`, not the check list.

I resolved it dispatcher-side rather than re-dispatching
(`pr-gate-loop.md` §"Dispatcher-side recovery"): both conflicts were pure
both-sides-appended blocks, so a union resolution is correct by construction —
but I verified it by **building** rather than by eye, since a union on a `dune`
file can silently drop or malform a rule:

```
BUILD_EXIT=0   RUNTEST_EXIT=0   ^FAIL: lines: 0
OK: token_usage_report_test -- all 50 assertions passed.
OK: scenario_runner flag drift test -- 63 checks clean.
```

Both merged rules fire. Pushing `7c7eeee3` moved the PR `dirty` → `behind` and
CI queued immediately, confirming the diagnosis.

**4. qc-structural then caught the fmt gate failing on *my* resolution.** I ran
`dune build` and `dune runtest` before pushing — but **not `dune build @fmt`**,
and the union left `trading/devtools/checks/dune` missing one blank line between
the two stanzas. Both stanzas parsed and both rules fired, so build and runtest
were green; only fmt was red, and `build-and-test` runs fmt, so CI went
`failure` at `7c7eeee3`. The reviewer named the omission exactly: *"for a
hand-resolved conflict in a `dune` file, fmt is the gate most likely to catch
it, and here it was the only one of the three that did."*

That is the correct generalisation and I'd been running a two-gate check where
three were needed. Fixed with `dune fmt` (one line, `840790a3`), then re-verified
all three: fmt 0, build 0, runtest 0, zero `^FAIL:`, 50 assertions + 63 checks.

This is the **fifth consecutive run** whose record shows a dispatcher instruction
or action being corrected rather than an agent's work. The 09-22 summary named
the pattern as "me asserting the state of a file from a narrow grep instead of
reading it"; today's instance is adjacent but distinct — **running a subset of
the gates and treating it as the gate**. Same family: a cheap proxy substituted
for the actual measurement.

**5. One reviewer asserted a gate verdict that did not exist.** The `7c7eeee3`
structural review concluded that qc-behavioral's *"APPROVED verdict covers the
unchanged script"* — but qc-behavioral had **never approved this PR**; its only
verdict was the NEEDS_REWORK at `d0c978be`. Had I acted on that sentence, #2927
would have merged with one gate never satisfied. I corrected it in the next
dispatch brief, and that reviewer retracted the claim by name in its posted
review. Worth recording because it is the precise mechanism by which a
three-gate rule degrades to two: not a gate being waived, but a reviewer
misreporting another gate's state.

**The ordering cost is the lesson, not the conflict.** Two same-day harness PRs
that both append to `harness.md` and `devtools/checks/dune` will always conflict
once the first merges — the second's QC verdicts are then invalidated by a merge
commit the author never wrote. Sequencing the merges, or having each agent
append to a distinct section, would avoid spending a QC pass on merge
correctness.
