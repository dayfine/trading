## Two environment defects, found by hitting them

### 1. "Never background your build" is an instruction agents cannot follow

Every writer brief has carried a prohibition on backgrounding the build, on the
premise that an unread build result is the same as no build. The premise is
right. **The instruction is impossible.**

The Bash tool **force-moves any command to the background at a 120-second
timeout**, and a cold `dune build` in this repo takes 10–20 minutes. So the
build gets backgrounded regardless of intent — and the completion notification
does not arrive in the shape agents wait for. **Three of four writer agents
stalled on this**, each ending a turn "standing by" for a result that would
never be delivered. One of them burned three turns this way.

This is the same failure the prohibition was written to prevent, caused by the
prohibition itself. What actually works, and what unblocked all three:

```sh
# launch detached, capturing the exit code to a FILE (no pipe — a pipe
# makes $? report the pipe's status, not dune's)
( ./dev/lib/run-in-env.sh dune build > /tmp/X.log 2>&1; echo $? > /tmp/X.rc )

# then poll in the SAME turn with short, instantly-returning calls
[ -f /tmp/X.rc ] && echo "DONE rc=$(cat /tmp/X.rc)" || echo "still running"
```

The `.rc` file is the completion signal. Every agent that was given this
finished. The correct standing instruction is not "don't background" but
**"background it, capture the exit code to a file, and don't end your turn
until you have read that file."** Blocked on `.claude/**`.


Two consequences. Operationally, dune-touching dispatches must be serialised,
which is a throughput ceiling this orchestrator does not currently model (it is
adjacent to #2300's `container-capacity-scheduling.md`, but that rule is about
*memory*, not the dune lock). Epistemically, this is a **failure mode that
manufactures false red gates** — the agent came within one step of reporting a
healthy PR as broken. I corrected the review before posting and recorded the
correction inline in it.

## I broke a merge gate

**I merged #2302 while its `build-and-test` check was still `in_progress`.**
Measured, on the merged tip `02de11c8`:

```
perf-tier1-smoke   completed    success     started 10:21:21  completed 10:24:27
build-and-test     in_progress  None        started 10:21:21  completed —
```

The merge returned `"merged": true` at 10:27Z. `.claude/rules/pr-merge-gates.md`
is unambiguous about this: *"If any line shows `pending` or `fail`, DO NOT merge.
This is non-negotiable even with `--admin` privileges."* It is the rule that
exists because #883 and #1113 each merged red and blocked main.

**Cause — a defect in my own polling loop, not a judgement call.** The shape I
used was:

```sh
for i in $(seq 1 24); do ... [ "$C" = "GREEN" ] && break; done
curl -X PUT .../merge          # <- runs unconditionally
```

When the loop *succeeds* it breaks and merges: correct. When it **exhausts its
24 iterations without ever going green**, it falls through to exactly the same
merge call. The loop gates nothing; it only delays. For #2265, #2301 and #2303
the loop happened to reach `GREEN` first (at iterations 19, 10 and 21
respectively) so those three merged legitimately — which is precisely why the
bug stayed invisible until a slower check exposed it. The fix is one line:

```sh
[ "$C" = "GREEN" ] || { echo "ABORT: CI not green"; exit 1; }
```

**Why the merge was not refused.** `main` has `build-and-test` +
`perf-tier1-smoke` as required checks with `strict: true`, so I expected the API
to reject this. It did not. That is worth a human look — either the protection
config has drifted, or the token carries a bypass. Either way, **the branch
protection is not the backstop it is assumed to be**, which makes the
orchestrator-side check load-bearing rather than belt-and-braces.

**Actual exposure is low, but that is not the point.** The identical content had
`build-and-test` **success** at `22bf212d`; the only delta on `02de11c8` was
`update-branch` merging main in. And #2302 is a comment-only change to one test
file. But "the content was probably fine" is the exact reasoning the rule
forbids, so I am recording this as a process failure rather than a near-miss.

**Outcome — main is green.** `build-and-test` on `main@700bdcda` completed
**success**, as did `perf-tier1-smoke` and `golden-custom-universe`
(`golden-sp500-5y` still running, as it is on every recent SHA). Zero open
`ci-red` watchdog issues. So the violation cost nothing this time.

That is the least interesting fact about it. A gate that is skipped and happens
to be green is indistinguishable, from the outside, from a gate that was
checked — which is why the rule is written as an unconditional. The loop defect
would have merged red just as readily.

### #2303 — strip whole-line comments before the universe-deps candidate scan

`check_universe_deps.sh` grepped for `repo_root)` without distinguishing comment
prose from real call sites, so a comment *quoting* the call syntax flagged its
own file. The tripwire has been disarmed by author discipline ever since.

The fix strips **only whole-line** `#` comments. That restriction is the design:
stripping `#`-to-end-of-line would introduce a false negative, because `#` in
shell is only a comment when it starts a word — `${var#prefix}` and `${#arr[@]}`
are expansions. Fixtures pin **both** directions, and the mutation run showed
the defect's blast radius was wider than filed (assertions 2 and 3 were polluted
too, not just the one flagged file). Before/after on the real tree: byte-identical
output, so no hidden coverage shift.

The agent also reported honestly that the item's suggested "reuse the existing
`strip_comments()` helper" **was not applicable** — that helper is an awk
function inside a paragraph-mode dune parser, a different process and a
different comment leader — and said so rather than quietly diverging.

**Then qc-behavioral rejected it, correctly, and this is the best catch of the
run.** The PR advertised assertion 9 as the guard against an over-eager fix that
"strips past end-of-line." The reviewer tested that claim instead of reading it:

| Mutation to `_strip_hash_comments()` | Result |
|---|---|
| `awk '$0 !~ /#/'` (drop any line containing `#`) | 8 passed, 2 failed — caught |
| `awk '{ sub(/#.*$/, ""); print }'` (strip `#`-to-EOL) | **10 passed, 0 failed — NOT caught** |

The guard was inert, for two compounding reasons: the fixture's `${var#prefix}`
noise sat on *standalone* lines carrying no `repo_root)`, so its survival was
unobservable; and the real call-site line put its `#` *after* `repo_root)`, so
truncating there left the match intact. A future "simplification" to
`sub(/#.*/,"")` would have passed the whole suite while silently reopening the
false-negative class — in a *cache-blindness* guard, which is the `H-CHECK-CACHE-BLIND`
failure mode where a stale cached PASS hides a check that stopped running.

The fix was one line, and the reviewer **verified it discriminated before
proposing it**: move the expansion onto the call-site line so its `#` precedes
`repo_root)`. The rework applied exactly that, left the shipped implementation
byte-identical (I verified the diff myself), and re-measured all three states —
the decisive mutation now fails assertion 9.

The re-review added one more piece of judgement worth keeping: assertion 10
co-fails under that mutation, which the author waved through as "a fine side
effect." The reviewer explained *why* it is acceptable rather than accepting the
framing — assertion 10's success is a conjunction (be detected as a candidate
**and** get an `OK:` line), so non-detection necessarily fails it, and the pair
stays jointly diagnostic: 9∧10 failing means detection is broken, 10 alone means
the rule-parsing path is.
