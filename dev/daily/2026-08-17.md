## Both rework agents failed CI on the same step, and the first one was my fault

Three reworks were dispatched. **Two of them came back CI-red on the identical
step** — `dune build @fmt`, the third of CI's three build commands:

| PR | rework push | `dune build` | `dune runtest` | `dune build @fmt` | unformatted file |
|---|---|---|---|---|---|
| #2357 | `e4cd97e1` | pass | pass | **exit 1** | `trade_audit.mli` (the docstring it rewrote) |
| #2352 | `48f1b1d5` | pass | pass | **exit 1** | `test_entry_stop_width_order.ml` (the test it added) |

**For #2357 the omission was mine.** My brief said *"one foreground `dune build`
— read the exit code; `.mli` comment edits should be a no-op"*. I never asked for
`@fmt`. For #2352 I did ask (*"Then `dune build @fmt` (exit 0 required; CI runs it
as a hard gate)"*) and it was missed anyway.

The mechanism is worth stating because it makes this predictable rather than
careless. `ci.yml`'s fmt step is **check-only, with no `--auto-promote`** — the
comment in the workflow says so. So an unformatted file **passes `dune build` and
`dune runtest` and fails only at the third step**. And the thing ocamlformat most
wants to reformat is *re-flowed prose*: it re-wraps `(** … *)` docstrings but
leaves plain `(* … *)` comments alone (`wrap-comments` is off). **A
docstring-only PR is therefore the exact shape that builds clean, tests clean, and
fails `@fmt`** — which is precisely what #2357 is.

The #2357 reworker put it back to me more sharply than I had it: *"the gap was
that my brief specified `dune build` as the gate while CI's gate is the
three-command sequence ending in `dune build @fmt`."* That belongs in the dispatch
template, not in my memory of one run.

Both were recovered in one round — #2357 via `dune fmt` (one file, no wording
changed), #2352 via `dune promote`. Cost: two wasted CI cycles and one extra
agent round trip, entirely avoidable.
