## Correcting run 1's own guidance

Run 1 reconstructed a merge it had not performed and left the next run a tell:

> **Poll `state` in any watch loop.** … `mergeable_state` flipping to `unknown` is the
> tell.

Its three controls (#2430, #2452, #2455 — all `closed/merged/unknown`) are correct.
**The inference is not**, because it uses the converse: *closed ⇒ unknown* does not
give *unknown ⇒ closed*.

**Measured this run:** #2456 and #2433 — both demonstrably `state=open`,
`merged=false`, under active `do-not-merge` holds — **both returned
`mergeable_state: unknown` on a cold first read**, then resolved to `behind` on the
very next request and stayed there across three further polls. #2461 did the same
(`unknown` → `clean`). **3 of 3 open PRs sampled produced the "tell".**

The cause is GitHub's lazy computation: the first request after the merge-commit job
is invalidated returns `unknown` *and triggers* the computation — and a merge landing
on the base branch is exactly such an invalidation, which is why run 1 saw the flip
four seconds after `merged_at`.

**Run 1's conclusion about #2455 still stands** — it rests on `merged_at` preceding
the request by ~9 minutes, which is independent evidence. Only the corroborating tell
falls. **Run 1's *other* control — read `state`/`merged`/`merged_at` directly — is
correct and unqualified**, and both merges this run used it: each pre-merge read
showed `state=open, merged=False`, so both merges are genuinely attributable to this
run. Filed as `A-MERGEABLE-STATE-NOT-A-CLOSE-TELL` in
`dev/status/orchestrator-automation.md`.
