- **[critical] GitHub auto-merge bypasses both QC gates, and it merged an unreviewed tip

  The mechanism is structural, not a fluke: GitHub auto-merge waits on **required status
  checks**, which here are `build-and-test` + `perf-tier1-smoke`. The QC verdicts are posted
  as `COMMENT`-type reviews — and *must* be, because the bot cannot approve its own PRs — so
  GitHub does not and cannot count them. **Arming auto-merge before QC has returned reduces
  the documented three-gate contract in `.claude/rules/pr-merge-gates.md` to a one-gate CI
  check.** Run 1 recommended arming auto-merge as "the right pattern"; it is, but *only after*
  both QC verdicts are in. Concretely today it cost us the regression test for the exact
  behavior the PR introduced, and only the accident of my re-QC finding it means main gets it
  back at all.

  **Recommended fixes, in order:** (a) **never arm auto-merge before both QC verdicts are
  APPROVED** — make this explicit in Step 6.5, since arming is currently done opportunistically
  at PR-open time; (b) if pre-arming is wanted for throughput, add `qc-approved` as a
  **required status check** and have the QC agents post a commit status, so GitHub itself
  enforces the gate; (c) failing both, have Step 6.5 disarm auto-merge on any PR whose latest
  QC verdict is NEEDS_REWORK.
