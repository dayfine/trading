## The reviewer found the defect inside its own fix

This is the finding of the run, and it is better than the one I asked for.

I dispatched qc-behavioral on #2721 with a specific hypothesis: that **`--dry-run`
fidelity** was the weak point — if dry-run diverges from the real path, the suite
pins a different program than the one that runs. The reviewer **cleared dry-run**
(all three things it skips *are* exercised in non-dry-run mode against a local
bare remote plus a mocked `curl`; six mutations against them go red) and then
found the real gap somewhere I had not looked.

It ran **28 mutations. 16 killed, 12 survived.** Two are critical:

**M23 — the publisher can publish nothing and report success.** Insert
`git reset -q --hard` immediately before the `git push`. Result: the script prints
`publish_daily_summary: PR #123 <url>`, **exits 0**, the branch exists on the
remote, and `git show ops/daily-2026-09-08:dev/daily/2026-09-08.md` →
`fatal: path does not exist`. **The suite reports 35/35 passed.**

That is `H-DAILY-SUMMARY-PR-LOST` — *the exact defect this PR exists to fix* —
reproduced **inside the replacement**, invisible to the replacement's own tests.
The cause is that the three "landed on the bare remote" assertions run
`git branch --list`, which pins the branch **name** and never that the summary is
**on** it. CP3 in one sentence: existence is not identity.

**M22 — the production code path is never executed.** Every fixture does
`git add && git commit` *before* invoking publish, so only the "already committed,
nothing to add" branch ever runs. Replacing the script's own `git add` + `git
commit` branch with `return 1` leaves the suite at **35/35 green**. In production
the orchestrator writes the summary as a **new, uncommitted** file — so the
untested branch *is* the production path. The shipped code handles it correctly;
it is untested, not broken. But "35 checks" was measuring a different program
shape than the one that runs.

A third survivor is the same disease: `ls -t` → `ls` survives **including the check
literally named "picks the newest `-runN` variant by mtime"**, because that
fixture's files sort identically under both orders. Against the real naming on
`main` today (`2026-07-28-run2/3/4.md`) the mutant resolves **run2** where the
shipped script resolves **run4** — publishing the day's *first* summary while
reporting success.

**Why this matters beyond one PR.** My own mutations passed (34/35, 33/35), and
qc-structural independently re-derived them and approved at quality 5. Three
separate measurements of the same claim, all green, and the thesis was still
unpinned — because we all mutated the guards the suite was *built around*. The
reviewer mutated the guards the suite **was not** built around. That is the
difference between confirming a test suite and testing it.

It also verified its own remediation: **one** new scenario in the production shape
(write the summary, do not pre-commit, assert sentinel content on the pushed
branch) passes against the shipped script and **kills both critical survivors**.
