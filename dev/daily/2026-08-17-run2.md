Read it in order. The step resets the runner to `e1d62260` — **main as it was at

`Switched to branch 'ops/daily-2026-08-17'` — **a stale local branch of the same
name, not `FETCH_HEAD`**. `Your branch is ahead of 'origin/main' by 1 commit`
confirms it: the local ref carries one commit, the remote carried more. The
budget commit lands on that outdated base and the push is correctly refused.

**This is a third, distinct failure mode for the same step**, and the previous two
diagnoses do not cover it:

| run | step 9 failure | mechanism |

The fix is the same shape as the one `A-SUMMARY-STALE-FALLBACK` and the

### #2362 — the assertion that could not fail

The PR adds scenario 40 to pin `consecutive_rework_count` end-to-end through the
empty-SHA degrade path. Its assertion was:

```sh
grep -q '"consecutive_rework_count": *1'
```

**That pattern is prefix-loose.** The reviewer forced the counter to **10** and
scenario 40 still **passed** — `10` contains `1`. The single assertion the whole
scenario exists for did not discriminate. (Fix, verified live: match the trailing
comma the JSON always emits.) Scenario 40 had also dropped the companion stdout
assertion that all five sibling count scenarios pair with their JSON grep.

The second finding is the more valuable one. The PR claimed the streak is capped
at 1 *"regardless of how many genuine reworks occur"*. The reviewer measured:

- **6 same-date calls → count stays 1** (so the 3-call fixture was *not* an
  artifact — the cap is real within a day);
- **the same calls across four successive dates → 1 → 2 → 3 → 4.**

So **#2339's `>= 3` escalation IS reachable through this path** — it fires on the
third consecutive day. `write_audit.sh`'s own docstring already said this
correctly (*"unreachable within a single day for a single branch"*); the PR body,
commit message, status-file note and scenario comment had all dropped the
qualifier. The item's *filing* text had the #2339 consequence right and its
*completion* text dropped it entirely.

The rework fixed both, and went further than asked: **new scenario 41 pins the
cross-date accumulation 1 → 2 mechanically**, converting the corrected prose into
an enforced contract — and that is the half #2339 actually depends on. Suite
58/0 → 59/0. The author re-ran the force-to-10 probe after fixing and confirmed
scenarios 40 and 41 now both go red.

### #2363 — a two-branch claim over a four-shape set

The PR reworded three comments that justify a linter exemption, replacing a claim
that had gone stale. The replacement was itself a universal:

> *every invocation either overrides `REPO_ROOT` to a temp fixture, or runs
> `env -u REPO_ROOT` from inside a fixture carrying its own `.claude` sentinel.*

The reviewer enumerated the invocation set and found **four shapes**:

| shape | sites | covered? |
|---|---|---|
| A: override → real temp fixture | ~55 | limb 1 ✅ |
| B: `env -u REPO_ROOT` | exactly 2 (sc. 27b, 28b) | limb 2 ✅ |
| C: override → deliberately **malformed** | sc. 29a/b, 30a/b, 31a/b | **neither** ❌ |
| D: `REPO_ROOT=''` → falls through to walk-up | sc. 29c, 30c, 31c | **neither** ❌ |

The decisive point is subtle and worth keeping: limb 1 is not *"overrides
`REPO_ROOT`"*, it is *"overrides `REPO_ROOT` **to a temp fixture**"*. Both
`_repo_root()` implementations guard on `[ -n "${REPO_ROOT:-}" ]`, so
`REPO_ROOT=''` **never takes the override branch** — it falls through to the
walk-up, the branch limb 2 describes, while not being an `env -u` site. Shape C
misses for a different reason entirely: the malformed value is `mktemp -u`, a name
reserved and never created, so it hard-errors at the `[ -d ]` guard before any
path is computed.

Sharpest form: **30c/31c are safe by exactly the same argument as 27b/28b, but the
wording attached that argument only to `env -u` sites.** Off by six sites — the
same defect class, one abstraction along. The `dune` comment was worse: it filed
29a–29c under limb 1 affirmatively and concluded *"Either way"* when there are
three ways.

The reviewer also caught that the author **had a correct formulation and shipped a
narrower one** — `dev/status/harness.md`'s own broader phrasing was right while the
comment it described was not.

The rework moved all three sites to a three-shape invariant, replaced the
drift-prone exhaustive `"(scenarios 27b and 28b)"` parenthetical with a
non-exhaustive form, and **retracted** the over-claim in the status file by
appending rather than amending, preserving the audit trail.

### What is new about these two

The class is not new — it is at nine instances in eight days. What is new is that
**both PRs were fixes for an instance of the class and committed a fresh instance
while doing it.** #2363 is the purest case available: a PR whose entire purpose is
to make one comment exactly true, shipping a second version of that comment which
is also not exactly true.

The practical lesson is narrower than "be careful". In both cases the author
enumerated a set correctly and then **wrote a summary sentence that quantified over
a different set than the one enumerated** — #2362 counted three same-date calls and
wrote "regardless of how many"; #2363 tabulated four shapes and wrote a two-branch
invariant. **The enumeration was right and the sentence drifted from it.** So the
check worth adding to briefs is not "enumerate the set" — that is already there and
it worked — but *"re-read your final sentence against your own table and confirm
they quantify over the same thing."*
